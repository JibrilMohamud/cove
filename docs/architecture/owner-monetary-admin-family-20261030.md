# Monetary commerce administration: private owner cutover (QA-only)

The three browser/API administrator operations **promotion update**, **gift card
issuance**, and **store-credit adjustment** formerly called direct D1 writers
from the API. Under the explicitly enrolled isolated QA owner, these now
delegate by authenticated typed private owner RPC. The existing direct
production path remains unchanged; production positive ownership stays
disabled.

## Security and money correctness
- The API requires the existing authenticated `commerce.manage` permission.
  The private owner independently re-queries the canonical active principal,
  current `commerce.manage` / `staff.manage` role permission, SSO provider/
  subject and required MFA level. Revoking an admin's role takes effect
  immediately for new monetary commands. A caller-provided staff identity
  without an authenticated private service binding cannot reach the owner.
- An `Idempotency-Key` header (16–150 safe characters) is mandatory for all
  three enrolled mutations. Gift codes are deterministically generated by
  owner-only HMAC over the command ID. Duplicate retries must produce the
  identical code and stored liability; key replay with different amount,
  currency, or expiration is denied.
- Credit ledger entries use a fixed operation-derived id. A negative change
  checks balance less existing checkout reservations in the *same SQL INSERT*
  and cannot race a separate application-level available-balance read.
  Replay cannot double post; conflicting changes are rejected.
- Promotion codes use the original canonical normalization and the existing
  product behavior of administrator upsert. Their canonical fields are read
  back before success; repeated same-payload writes are safe. Concurrent
  promotion edits are still last-writer-wins by design. Promotion command
  history is not a separate immutable admin audit journal; a stronger
  production owner will need command-digest history before production cutover.
- A missing owner, false acknowledgement, bad role, no idempotency key, QA
  lease expiration, or provider mismatch fails closed with no enrolled
  fallback into the caller's D1.

## Evidence and limits
The full canonical D1 migration suite now exercises these three owner
commands with live SQLite: MFA/SSO/role enforcement and revoke, gift issuance
and repeated retry, changed replay denial, store-credit idempotence,
insufficient funds, promotion normalization and readback, and production
database identity denial.

All original 56 commerce writer SQL literals, functions and dispositions
remain in the unenrolled production compatibility branch. The independent
audit still reports **371 owner-command-required among 426**, with no
certification of production exclusivity, live Stripe settlement or reversal,
or deployed rollback. Neither the production canonical D1 binding nor the
production legal owner is changed in this PR. After all remaining commerce
families are production-capable, actual privilege retirement and real
positive/negative paid-media tests are mandatory before 371 -> 315 can be
recorded as a legitimate cutover.
