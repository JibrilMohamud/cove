# Detached staging and temporary production maintenance

Provider resource inventory on 2026-11-28: seven new detached D1 databases, three new R2 buckets and one KV namespace. Exact identifiers are in `infra/detached-staging-resources.json`. Resources are newly provisioned, not populated or accepted. The old resources remain intact. Never use a full production dump, customer data, or production service credentials in detached QA.

Nine actual production maintenance workflows use `COVE_CF_PROD_MAINTENANCE_TOKEN` instead of the broad staging secret. The existing protected environment and exact reviewed main dispatch remain mandatory. The token must be newly issued for the exact profile's Worker UUID set with only Individual Workers Editor, expiring within two hours; independent account inventory proves the actual supplied credential. Revoke it after the maintenance run and remove the secret. Do not install a standing equivalent. The old internal environment spelling in BioSync scripts is only a compatibility alias; the secret source is the new temporary credential.

The detached catalog copy uses the original reviewed column projection, a dedicated QA-only schema initialization, a separate production D1 Read principal and QA data-plane read/deploy principals. Its new receipt does not admit the historical production-account snapshot's receipt. The original protected source remains intact until all its consumers migrate; no completed acceptance is implied.

A dedicated `COVE_CF_QA_DATA_PLANE_READ_TOKEN` is required: account-scoped to the detached QA account only, D1 Read, Workers R2 Storage Read, Workers Scripts Read, Workers KV Storage Read. No edit, token-management or production-account scope. Put it in the existing protected GitHub Actions environment, not source or logs. Verify provider identity and permissions separately. Existing QA D1/R2 mutation and Worker deployment principals remain in the detached account only.

The source inventory enumerates all workflow YAML files and refuses zero-dependency certification if the legacy secret is referenced or an unresolved computed secret access exists. It does not prove historical workflow retirement, provider revocation, or hosted acceptance. Run it in audit mode during migration; require zero after all consumers are migrated. Production-account native SSR and custom-domain canary, full-catalog previews, synthetic capacity, publication capture/ledger and the legacy backend probe still require their own detached replacement and hosted acceptance. Same-account service bindings cannot be assumed to work across accounts; production read access must remain separately authenticated, read-only, and never grant native primary D1 access.

**No revocation is authorized by this draft.** A new resource ID, source change, or skipped protected job is not a hosted acceptance receipt. Do not run legacy binding deployment or cutover merely to exercise credentials.
