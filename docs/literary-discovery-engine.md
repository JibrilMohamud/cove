# Literary discovery engine

Cove's discovery baseline now connects book intelligence, taste modelling, retrieval, ranking, and feedback. This is working product code; Kindle parity and calibrated enjoyment accuracy have **not** been established.

## Serving and reader experience

`POST /recommendations/discover?visitor=<uuid>` accepts `{query, controls?, limit?}`. It uses the same territory eligibility, account exclusions, attribution, model registry, experiments, hydration and recommendation cards as the home and book recommendation APIs. The bookstore exposes search intent, explicit likes/dislikes, reading commitment, adventure, and saved taste controls. Anonymous readers can use session controls. Authenticated readers can save or clear preferences and give satisfaction feedback. Empty matches are reported rather than replaced with unrelated popular books.

`GET/POST /recommendations/taste` read or replace the authenticated reader's explicit preferences. Saved controls apply when personalization is enabled; session controls are usable independently. Intent never writes persistent preferences. The existing privacy and profile-reset endpoints remain authoritative. Full reset clears saved controls; learned reset sets a learning boundary so old reading history does not immediately reconstruct the erased profile. Account export includes controls/events/feedback; account erasure removes these and the boundary.

## Five systems

| System                | Implementation                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Book intelligence     | Existing validated, versioned literary profiles and reading estimates. Migration 0069 projects cited themes, moods, styles, geography and atmosphere into an inverted feature index. Insert/update/delete triggers keep it current. Failed and ungrounded dimensions are excluded.                                                                                                 |
| Reader model          | Explicit preferences plus confidence-weighted long-term (180-day half-life) and recent (14-day half-life) evidence. Independent books determine confidence. Latest explicit satisfaction supersedes implicit signals for that book. Repeated implicit actions are capped. Pauses are neutral. Existing reading states seed readers whose book has no recommendation event history. |
| Retrieval             | Indexed literary taste, explicit-intent and anchor-book channels supplement the existing affinity, item-neighbor, co-read, collaborative, regional-quality and optional external retrieval channels. Literary retrieval is independent of popularity. New multi-ID DB queries are chunked.                                                                                         |
| Ranking/reranking     | Evidence-weighted literary compatibility and existing hybrid signals; semantic-tag overlap, author and series diversity; work-level edition deduplication; known series prerequisites; language, ownership, territory and known dislike exclusions. A validated optional learned satisfaction ranker can replace baseline scoring through the existing model registry.             |
| Feedback and learning | Explicit `loved`, `not_for_me`, `recommend`, `abandon` and bounded 1–5 ratings supplement existing progress/completion events. Attributed events validate the served book and account. Served feature snapshots enable time-separated training without reconstructing features from future reader history.                                                                         |

## Learning and evaluation

`GET /admin/recommendations/discovery-dataset` requires `recommendations.manage`. It exports up to 5,000 explicitly labelled, visible, account-attributed outcomes from currently consenting accounts. Missing outcomes and neutral ratings are not negatives. Reader pseudonyms rotate per export. Treat exported datasets as private; delete them when no longer needed and regenerate after erasure/consent changes. This is an opt-in operator workflow, not a scheduled personal-data export.

Train with `node scripts/discovery/train-ranker.mjs rows.json report.json`, supplying the export's `rows` array. The trainer requires at least 100 training examples, 30 holdout examples, 20 training readers and both satisfaction classes in both sets. It uses a chronological split, purges training labels observed only during the holdout period, deduplicates request/book labels and reports Brier score against a satisfaction-prior baseline. Synthetic fixtures validate mechanics only.

The artifact is an evaluated logistic baseline, not proof of calibration or causal lift. Activation is manual via the existing draft/active recommendation-model API, using `config.discoveryRanker = report.model`. Review temporal metrics, subgroup performance and reader studies before activation; use existing randomized experiments to establish online benefit. Artifacts do not contain reader identities or histories. The baseline remains active when no validated artifact is configured. Never label baseline scores as enjoyment probabilities.

`GET /admin/recommendations/status` includes profile coverage, indexed books/features, explicit feedback counts and baseline readiness. Existing operational telemetry retains candidate-channel counts, latency, scorer fallback, model/experiment assignment, visible impressions, clicks, catalog coverage and source entropy. Each request records the discovery policy version and served feature snapshot.

## Important limits and next release gates

- Book-profile coverage is inherited from the existing enrichment pipeline and its inference budget. A metadata-only catalog is not a fully understood catalog. Coverage must be measured in production; do not describe all books as fully analyzed.
- The local intent parser supports **exact evidence tags** and clauses such as `less war` and `under 4 hours`. It is not a general conversational LLM. There is no newly provisioned semantic embedding/ANN service, neural sequence model or character/influence graph. Existing external retrieval/ranking adapters and optional semantic search remain separate integration points.
- Experience measures such as prose complexity, dialogue density and pacing are not invented from energy or tension. Dedicated validated extraction and indexed dimensions are needed before making those promises.
- Unknown advisories are not proof of safe content. Avoid controls suppress known tagged content; they cannot guarantee absence in incompletely profiled books. Strict age/advisory certification needs verified supplier fields and a fail-closed suitability workflow.
- Reading-time limits require a supported estimate with an upper range bound; partial-text lower bounds and catalog priors are insufficient. Duration is an estimate, not a promise.
- Exploration applies only after hard constraints. Its local implementation is controlled diversity/exploration, not a learned contextual bandit. Learned long-term satisfaction, unbiased exposure policies and production latency at million-book scale still need outcome data and benchmarks.
- Temporal Brier evaluation is a first gate. Add ranking recall/NDCG, per-reader cohorts, position/selection-bias analysis, novelty and successful unfamiliar-author outcomes before claiming commercial recommendation accuracy. Kindle superiority requires comparable evidence.

## Verification

`npm run test:literary-discovery` exercises real migrated SQLite/D1-compatible bindings, real catalog hydration, index freshness/deletion, evidence abstention, preference retrieval, click caps, negative satisfaction, session isolation, rating bounds, attribution, opt-out, reset and synthetic chronological trainer leakage checks. Browser QA covers actual form submission, empty state, keyboard clearing and scoped axe accessibility across configured device/browser projects. Existing recommendation, literary-profile, music-matching, privacy and account-erasure checks remain required.
